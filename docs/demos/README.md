# Demo videos

Marketing-quality screencast mp4s of the app, recorded from a disposable harness so the timeline is
reproducible. Used for in-app embeds and the marketing site (GitHub does not render repo-linked
`.mp4` files in READMEs — convert to a preview GIF when README embedding is needed).

## Run

```bash
bun run videos                  # record every scenario
bun run videos --dry            # replay the scenarios without writing the mp4 (timing only)
bun run videos --only library   # scenarios whose name contains "library"
```

Prerequisites:
- One-time: `bunx playwright install chromium` (Playwright ships its own chromium under `~/Library/Caches/ms-playwright/`; we do not reuse the Playwriter-managed Chrome).
- The package `playwright-recorder-plus` ships its own ffmpeg binary via `ffmpeg-static`; no system ffmpeg required.

## Architecture

The runner is `scripts/video-capture.ts`; scenarios are declared in `scripts/video-scenarios.ts`.

- **Harness reuse**: same scratch `DATA_DIR` boot as the e2e and screenshot pipelines
  (`scripts/lib/app-boot.ts` → `bootApp('videos')`). Provider env vars are stripped, so the
  recording always exercises the degraded contract (deterministic import parser, no classifier).
- **Driver**: a separate Playwright Chromium instance is launched by the runner — Playwright is a
  *capture-only* dev dep here. The e2e and screenshot harnesses stay on Playwriter.
- **Recorder**: `playwright-recorder-plus`'s `attachRecorder(page, { path, autoStart: false })`
  wraps Playwright 1.59+'s experimental `page.screencast`. Two-pass pipeline: real-time H.264
  ultrafast first pass cannot fall behind; second pass produces the final mp4 (H.264 / mp4 picked
  from the `.mp4` extension).
- **Pre-roll vs record**: the first `navigate` step of each scenario runs **before** recording
  starts so the screencast never captures the empty boot frame. Subsequent steps (including the
  first step's `holdMs`) run inside the recorded timeline.

## Scenarios

Currently one scenario is defined:

| Name | Theme | Length | What it shows |
| ---- | ----- | ------ | ------------- |
| `library-import` | light | ~7s | Seeded library → navigate to Import → paste markdown → Extract → commit → library updates |

The scenario spec is a `Step[]` where every step is paced by waiting on a selector *before* moving
on (no fixed sleeps between actions — CDP screencast is real-time, so an action issued before the UI
has settled is captured before the UI reacts). `holdMs` is a *visual* tail hold for the viewer.

Selectors are Playwright Locator strings (CSS, `role=`, `text=`, `aria-label=`, etc.); the page's
own `aria-label` attributes are reused for stability. To avoid the sidebar's `Import` nav button
matching the page's commit `Import N bookmarks` button, the commit step is scoped to
`[aria-label="Extracted bookmarks"]`.

## Output

mp4s land in `apps/web/public/demos/` (gitignored; regenerate locally). `preview.html` is committed
and embeds every mp4 with `<video controls>` for in-app review.

```text
apps/web/public/demos/
├── preview.html                  ← committed, in-app review grid
└── *.mp4                         ← gitignored, regenerated by `bun run videos`
```

## Hard-won gotchas (applied in `scripts/video-capture.ts`)

- **Viewport height ≥ 720.** CDP screencast frames mismatch below 720 and the output is blank. The
  runner uses `1280×720`; `playwright-recorder-plus` requires the same.
- **`--force-device-scale-factor=1` on Retina hosts.** Without it, frame size is wrong. The runner
  passes it as a Chromium launch arg **and** as `context.deviceScaleFactor`.
- **CDP screencast does not capture the OS cursor.** A faux cursor dot is injected via
  `context.addInitScript`; it also serves as a continuous-frame keepalive (a static page stops
  emitting screencast frames after ~200ms, which would leave white gaps in the recording).
- **GitHub does not render repo-linked `.mp4` in READMEs.** Embed via animated GIF preview (run
  `ffmpeg` palettegen pass over the mp4) when README embedding is needed; the canonical file stays
  mp4.
- **Do not add demo mp4s to the service-worker precache.** The default Workbox `{js,css,html}` rule
  is fine; just don't add a video rule.

## Why a separate driver (Playwright, not Playwriter)?

The e2e and screenshot harnesses are on Playwriter (project standard; see AGENTS.md Browser QA).
Video capture needs:

1. The Playwright `Page` API and the experimental `page.screencast`.
2. Programmatic control over the recorder lifecycle (start / stop / finalize).

Playwriter's relay daemon doesn't expose `page.screencast` or a recorder interface, so a separate
Playwright instance is the minimal addition. Playwright is loaded only from
`scripts/video-capture.ts`; the e2e and screenshot pipelines are unaffected.

## Drift / known limits

- The seeded dataset kicks off background enrichment on boot
  (`enrichment.jobsPending: 49`); the screenshot timing races the first wave of scrape/screenshot
  jobs. The video harness shares the same race for the library frame at the start, so some
  thumbnails may be placeholders. Pre-existing — not introduced here.
- Marketing-site sync is **out of scope** (known drift; remindsite uses `public/demos/preview.html`
  locally, marketing site hand-copies 3 light mp4s). Add an auto-sync script only when asked.
